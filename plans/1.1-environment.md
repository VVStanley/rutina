# 1.1. Окружение и запускаемый каркас

## Результат

Локальный FastAPI работает с PostgreSQL через Docker Compose. Отладочный APK запускается на одном Huawei P60, получает ответ от API по домашнему Wi-Fi и показывает русский или английский интерфейс по системному языку. Вход, покупки и сценарий на двух телефонах относятся к шагам 1.2–1.4. [Основной план](MASTER_PLAN.md) · [Критерии приёмки](../docs/ROADMAP.md#i1-окружение-и-запускаемый-каркас)

## Порядок работ

Размещать файлы по [структуре проекта](../docs/ARCHITECTURE.md#структура-проекта).

1. **Сервер.** Создать `server/` с FastAPI на Python 3.13. В `compose.yaml` описать API и PostgreSQL 17 с именованным томом, проверкой готовности БД и запуском API после её готовности. PostgreSQL доступна внутри сети Compose. В `compose.local.yaml` задать публикацию API по умолчанию на `127.0.0.1:8000` с возможностью явно указать LAN-адрес для телефона. Настройки читать через Pydantic Settings, пример переменных хранить в `.env.example`, локальные значения — в `.env` вне Git. Зависимости закрепить в `uv.lock`. Первую миграцию создать на шаге 1.2 вместе со схемой учётных записей и домов.
2. **Контракт.** Добавить `GET /health`. API выполняет `SELECT 1` через SQLAlchemy и возвращает `204` при доступной БД или `503` с кодом `database_unavailable` при недоступной БД. Проверка целиком ограничена тремя секундами, включая получение соединения из пула. Неожиданная ошибка даёт общий `500`. Возвращать `X-Request-ID` и записывать тот же идентификатор в лог.
3. **Android.** Создать в `android/` один модуль Compose. Использовать JDK 17, Gradle Wrapper 8.13, AGP 8.13.2, Kotlin 2.3.21, `minSdk` 31, `compileSdk` и `targetSdk` 36. Для тестовой и семейной серий APK использовать разные постоянные `applicationId` и ключи подписи. В каждой серии увеличивать `versionCode` между выдаваемыми сборками и подписывать их тем же ключом. Ключи и их резервные копии хранить вне репозитория. Семейный APK установить отдельно до ввода реальных данных. В 1.1 настроить и проверить тестовую серию. Закрепить Compose BOM `2026.04.01` и версии остальных зависимостей в каталоге Gradle. [Совместимость AGP](https://developer.android.com/build/releases/agp-8-13-0-release-notes) · [Совместимость Kotlin](https://kotlinlang.org/docs/gradle-configure-project.html) · [Compose BOM](https://developer.android.com/blog/posts/whats-new-in-the-jetpack-compose-april-26-release)
4. **Проверочный экран.** Кнопка «Проверить подключение» запускает один запрос. `ViewModel` показывает ожидание, успех, недоступность сервера или ошибку API. После сбоя кнопка снова доступна. Тексты вынести в английские ресурсы по умолчанию и русские `values-ru`. Адрес передавать при сборке через `-PrutinaApiBaseUrl=http://<LAN-IP>:8000`. Разрешить обычный HTTP только в `debug`-варианте. [Настройки сети Android](https://developer.android.com/privacy-and-security/security-config)
5. **Команды разработчика.** Добавить корневой `Makefile` с целями `help`, `up`, `down`, `status`, `logs`, `fmt`, `check`, `test` и `apk`. Локальные цели Compose явно используют `compose.yaml` и `compose.local.yaml`. `make down` сохраняет именованный том PostgreSQL. Описать штатные команды в `README.md`. [Назначение команд](../docs/ARCHITECTURE.md#команды-разработки)

## Проверка и завершение

- **Сервер.** Запустить `ruff format`, `ruff check`, mypy и pytest. Проверить `204` с отдельной одноразовой PostgreSQL без опубликованного порта. Для этой проверки достаточно пустой БД без миграций. В модульном тесте воспроизвести недоступность БД и проверить `503`, код ошибки и заголовок `X-Request-ID`. После запуска локального Compose подтвердить `204` запросом с компьютера.
- **Android.** Выполнить `ktlintFormat`, `ktlintCheck`, `lintDebug`, `testDebugUnitTest` и `assembleDebug`. Проверить переход из ошибки в успех при ручном повторе. Исполнитель готовит APK и чек-лист. Проверить на Huawei установку следующего тестового APK поверх предыдущего без удаления приложения. Пользователь устанавливает APK на один P60, проверяет успех по Wi-Fi, ошибку при отключении Wi-Fi и повторный успех после включения. Затем меняет системный язык с русского на английский, повторно открывает приложение и проверяет подписи и результат запроса. Для прогона достаточно телефона без Google Play services.
- **Makefile и Compose.** Сверить `make help` с доступными целями. Проверить запуск, статус и логи через Makefile. После `make down` и повторного запуска убедиться, что PostgreSQL использует прежний том, а `GET /health` снова возвращает `204`. Проверить, что штатные команды форматирования, проверок, тестов и сборки APK вызывают настроенные инструменты проекта.
- **Документация и статус.** При реализации закрепить версии и команды в [README](../README.md), применить [rutina-code-validation](../.agents/skills/rutina-code-validation/SKILL.md) и записать здесь фактические результаты. Если остался прогон на телефоне, поставить «ожидает проверки». После успешного прогона завершить 1.1 и перенести указатель на 1.2.

## Приёмка на Huawei P60

Подготовка описана в [README](../README.md#проверки-и-тестовый-apk). Нужны работающий локальный API, один P60 в той же сети и два подписанных тестовых APK с разными `versionCode`. Проверяющий выполняет сценарий без учётной записи.

1. Установить первый APK на P60 с русским системным языком и открыть его. Нажать «Проверить подключение». Появляется сообщение об успешном подключении.
2. Отключить Wi-Fi и мобильные данные и повторить запрос. Появляется сообщение о недоступности сервера. Включить Wi-Fi и нажать кнопку ещё раз. Появляется сообщение об успешном подключении.
3. Установить второй APK поверх первого без очистки данных и удаления приложения. Установка и запрос к API проходят успешно.
4. Переключить язык системы на английский и снова открыть приложение. Кнопка называется `Check connection`, после нажатия отображается `Connected to the server.`

## Прогресс и ближайшее действие

Добавлены FastAPI с SQLAlchemy, `GET /health` с идентификатором запроса, конфигурация Compose, двуязычный экран Android, тесты и `Makefile`. Тестовому APK назначен `app.rutina.test`, для его сборки предусмотрен отдельный постоянный ключ.

- `server/uv.lock` сформирован и проверен командой `uv lock --check`. На Python 3.13.15 прошли Ruff 0.15.22, mypy и три модульных теста API.
- `docker compose config` подтвердил публикацию API на loopback, переопределение LAN-адреса, именованный том и изоляцию тестовой БД. Для локального Docker понадобилась свободная подсеть в `compose.local.network.yaml`, поскольку пул подсетей по умолчанию исчерпан. Сборки API и интеграционных тестов используют общий кэш BuildKit для пакетов Python.
- `make test-db` прошёл на отдельной PostgreSQL 17 и очистил тестовые ресурсы. В локальном Compose с PostgreSQL 17.12 запрос на `127.0.0.1:8000` дал `204 → 503 → 204` при остановке и восстановлении БД. `X-Request-ID` совпал с журналом во всех трёх случаях. Проверены `make status` и `make logs`. После `make down` и повторного `make up` сохранилась та же БД, подтверждено по идентификатору кластера, API снова вернул `204`.
- Gradle Wrapper пересоздан из Gradle 8.13. Контрольные суммы JAR и дистрибутива совпали с опубликованными. `make fmt` и `ktlintCheck` прошли. Статически проверены русские и английские ресурсы и Android-манифесты. Подготовлен постоянный тестовый ключ подписи и его локальная резервная копия вне Git. [Контрольные суммы Gradle](https://gradle.org/release-checksums/)
- Установлены Android SDK Platform 36 ревизии 2, Build Tools 35.0.0 и Platform Tools 37.0.3. `adb version` подтвердил запуск. После добавления иконки и правил исключения данных из системного резервирования и переноса прошли `make fmt`, `make check`, два теста Kotlin и обе сборки `make apk`. Android Lint выдал десять уведомлений о доступных обновлениях версий. При первом прогоне AGP предупредил о более новом формате XML метаданных SDK.
- `android/app/build/outputs/apk/qa/rutina-test-v1.apk` и `rutina-test-v2.apk` имеют `versionCode` 1 и 2, одинаковые `applicationId` `app.rutina.test` и сертификат подписи. `apksigner` проверил оба файла для API 31, `aapt` подтвердил `minSdk` 31, ARM64, русскую и английскую локализации и запускаемую Activity. В обоих файлах проверен адрес `http://192.168.0.22:8000`. Локальный API на этом адресе запущен и возвращает `204`.

- 28 ноября 2026 года пользователь проверил каркас на Huawei P60. Скриншоты подтверждают русский и английский интерфейсы, успешное подключение к локальному API, сообщение о недоступности сервера и успешный запрос после ошибки. Пользователь подтвердил установку APK `0.1.2` поверх `0.1.1` без удаления приложения.

## Повторная проверка после ревью

- **REV-1.** Асинхронная проверка БД имеет общий дедлайн. На отдельной PostgreSQL запросы с ранее открытым и с новым соединением вернули `503 database_unavailable` за 3,01 секунды с `X-Request-ID`. После возобновления работы БД ответ снова был `204`.
- **REV-2.** Проверке готовности PostgreSQL задан начальный период в три минуты. На одноразовом Compose-стеке с задержкой старта БД на 55 секунд API запустился с первой команды и вернул `204`.
- **REV-3.** Android сопоставляет HTTP-статус с кодом в JSON. Штатные коды дают типизированные результаты, ответы вне контракта получают отдельный результат в слое данных. Kotlin-тесты покрывают оба кода, отсутствующий и неизвестный код, несовпадение статуса и кода. В проверке HTTP-клиента на JVM `204` дал успешный результат, а `503` с HTML и `502` с JSON были распознаны как ответы вне контракта.
- Офлайн прошли проверка `uv.lock`, Ruff, mypy, четыре модульных и один интеграционный тест Python, `ktlintCheck`, Android Lint, четыре Kotlin-теста и сборка APK. `android/app/build/outputs/apk/qa/rutina-test-v3.apk` имеет `versionCode` 3 и ту же подпись, что `0.1.2`.

Для повторной проверки установить `0.1.3` поверх `0.1.2` на Huawei P60 по [чек-листу](#приёмка-на-huawei-p60). На обновлённой сборке проверить подключение, сообщение при потере связи и повторное подключение. После прогона перейти к [шагу 1.2](1.2-login.md).
