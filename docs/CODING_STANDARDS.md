# Правила программирования

Правила обязательны для Python-бэкенда и Android-клиента на Kotlin. Поведение приложения определяет [PRODUCT.md](PRODUCT.md), устройство системы — [ARCHITECTURE.md](ARCHITECTURE.md).

## Обязательные проверки после изменения кода

1. Сразу после реализации запустить форматтер и линтер каждой затронутой части проекта. Автоматическое форматирование и исправления ограничить областью задачи.
2. Исправить все замечания в области задачи. После правок снова запустить форматтер и линтер и убедиться, что проверка форматирования и линт проходят. Замечания за пределами задачи указать отдельно, если они мешают проверке. Запрещено отключать правила или добавлять подавления ради успешного прогона.
3. Перед завершением проверить типы при изменениях Python, запустить компиляцию при изменениях Kotlin и выполнить тесты затронутых сценариев. Сообщить, какие проверки прошли и какие не удалось выполнить.
4. Проверить расположение новых файлов и направление зависимостей по [структуре проекта](ARCHITECTURE.md#структура-проекта).

Подключить форматтер, линтер и проверку типов с первого запускаемого каркаса. Для Android запускать форматтер Kotlin и Android Lint. Версии инструментов и команды проверок закрепить при подготовке каркаса и описать в [README.md](../README.md).

## Слои и зависимости

- Держать роуты FastAPI тонкими. Обработчик принимает типизированные входные данные, получает зависимости и контекст запроса через DI, вызывает одну прикладную операцию и формирует HTTP-ответ. Сериализация ответа работает с готовым результатом операции. Запрещено выполнять SQL-запросы напрямую или через ленивую загрузку ORM, управлять транзакцией и принимать бизнес-решения в обработчике.
- Прикладная операция проверяет права на действие и доступ к дому, применяет бизнес-правила и определяет границу транзакции. Запросы SQLAlchemy на чтение и запись, включая фильтрацию, соединения и блокировки, находятся в `db/queries/`. Переиспользовать запрос через прямой импорт из его модуля. Проверять направление импортов при ревью. Код хранения участвует в транзакции операции. Решение о фиксации или откате всей операции принадлежит прикладному слою. [Расположение серверного кода](ARCHITECTURE.md#сервер) · [Правила размещения](ARCHITECTURE.md#правила-размещения)
- На Android Compose отображает состояние и передаёт действия пользователя. `ViewModel` подготавливает состояние экрана и вызывает операции. Вызовы API, запросы Room и синхронизация находятся в слое данных. Сервер проверяет права и подтверждает изменения, телефон хранит локальную копию для чтения по правилам продукта. [Границы компонентов](ARCHITECTURE.md#границы-компонентов)
- Применять внедрение зависимостей (DI). Передавать зависимости явно через параметры или конструктор, собирать их в точке входа приложения. На HTTP-границе можно использовать `Depends`. Простой функции доступа к данным достаточно, если она решает задачу. Контейнер DI и дополнительные интерфейсы вводить при обоснованной необходимости.
- Соблюдать DRY и разделение ответственностей. У бизнес-правила или инварианта один владелец. Выделять общий код, когда потребители должны меняться вместе. Похожие по форме, но независимые операции могут оставаться отдельными. Выбирать самое простое решение для текущего сценария.

## Типы и статусы

- В Python явно указывать типы параметров и результатов всех функций и методов, включая `None`. Для структурированных данных использовать объявленные модели, например `dataclass` внутри приложения и Pydantic для JSON на границе API. Функции проекта возвращают объявленные типы. Запрещены возвраты `dict` и обход типизации через `Any`. На внешней границе проверять данные и преобразовывать их в типизированную форму.
- В Kotlin использовать `data class` для структурированных данных, `enum class` для конечных наборов значений и явные типы результатов на границах компонентов. Для однозначных локальных выражений подходит вывод типов. Отсутствие значения выражать nullable-типом и обрабатывать явно. Возврат `Map` вместо модели с известными полями запрещён.
- У каждого набора статусов, ролей и других конечных значений один источник в модуле-владельце. Например, строковое значение `pending` объявляется в Python `StrEnum`, а модель БД, значения по умолчанию в коде, запросы, переходы и тестовые фабрики используют `Status.PENDING`. Ограничения текущей схемы должны соответствовать enum. Android получает общие значения из контракта API без ручного копирования. Механизм получения клиентских типов выбрать при реализации первого обмена.
- Выпущенная миграция хранит значения своей версии. Тест контракта может независимо проверять точное значение, передаваемое в API или сохраняемое в БД. Переходы между статусами определяет прикладная логика. Подписи статусов для пользователя берутся из ресурсов локализации.

## Настройки и зависимости

- Использовать одну типизированную схему Pydantic Settings для `local`, `test` и `prod`. Значения у каждой среды свои, код приложения и структура настроек общие. Чтение настроек централизовано, обязательные параметры проверяются при запуске. Локальный `.env` хранится вне Git. Поля описываются в `.env.example` без секретов. Рабочие секреты передаются извне. Адрес API на Android задаётся конфигурацией сборки.
- Параметры среды выносить из кода в настройки. Значения с предметным смыслом именовать, единицы указывать в названиях (`timeout_seconds`, `amount_kopecks`). Обычные числа с очевидным смыслом допустимы. Пользовательские тексты Android хранятся в ресурсах русского и английского языков.
- Python-зависимости объявлять в `pyproject.toml` и фиксировать в `uv.lock` через `uv`. Использовать один lock-файл для локальной и рабочей сборки, инструменты разработки и тестирования держать отдельной группой. На Android использовать Gradle Wrapper, версии библиотек и плагинов объявлять в `gradle/libs.versions.toml`.

## Ошибки и логирование

- Все собственные исключения Python наследуются от `AppError`. Конкретные исключения определять рядом с соответствующей операцией или предметной областью. Перехватывать исключение для восстановления, преобразования на границе или добавления необходимого контекста. При преобразовании сохранять исходную причину.
- HTTP-граница централизованно преобразует ожидаемую ошибку в HTTP-статус и стабильный код в типизированном ответе. Неожиданный сбой возвращает общий `500`. Android обрабатывает код API в слое данных и передаёт в интерфейс типизированный исход. Сообщение берётся из ресурсов. Прикладная логика не зависит от HTTP-типов.
- Настраивать структурированное логирование при старте. Записывать уровень, имя события и безопасный контекст. Для HTTP-запроса указывать `request_id` и возвращать его в ответе. Неожиданный сбой регистрировать один раз на границе операции. Для ожидаемого отказа достаточно кода без стектрейса. Не записывать пароли, токены, тела запросов и семейные данные.

## Тесты и совместимость

- Модульные тесты запускаются без БД. Для обычных интеграционных тестов один раз на запуск готовить отдельную PostgreSQL, применять Alembic и загружать воспроизводимый `seed` с вымышленными данными. Изменения каждого теста изолировать откатом его транзакции. Порядок тестов произвольный.
- Сценарии, где требуется настоящий коммит, несколько соединений или проверка миграций, выполнять отдельными группами на изолированных тестовых данных. Для затронутых операций записи проверять применимые риски, включая права и изоляцию домов, повторную отправку и конкурентные изменения. Android-проверки на целевых телефонах запускать отдельно от быстрых тестов.
- Изменения схемы проводить через миграции Alembic и Room соответственно. При изменении схемы проверять создание новой БД и обновление с предыдущей версии с сохранением данных. При изменении API проверять затронутые сценарии установленного APK.
