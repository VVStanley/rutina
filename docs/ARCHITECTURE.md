# Архитектура

## Статус

Зафиксированы согласованный стек, структура проекта, основные границы, правила обмена B07 и целевая среда B09. Каркас сервера и Android создаётся на шаге 1.1. Схема данных, конкретные контракты операций и формат обмена проектируются по шагам. Общие правила идентификаторов, сессий и OpenAPI уже определены. Ответы брифов ведутся в [реестре](OPEN_QUESTIONS.md).

Схему PostgreSQL и локальную модель Room проектируем по мере реализации шагов плана. Общие правила и проверки описаны в [соглашениях по разработке базы данных](database/DATABASE_CONVENTIONS.md).

## Согласованный стек

- Android: Kotlin и Jetpack Compose.
- Локальное хранение: Room поверх SQLite.
- Фоновое обновление данных: WorkManager; периодическое получение изменений согласовано в B07.5, частоту выбрать перед реализацией. Очередь офлайн-изменений в MVP не входит.
- Сервер: Python, FastAPI и Pydantic.
- Работа сервера с БД: SQLAlchemy.
- Миграции серверной БД: Alembic.
- Серверная БД: PostgreSQL, в том числе в локальной разработке.
- Запуск серверной части локально и на одном рабочем сервере: Docker Compose.

Django и Django REST Framework не используются. Клиентская и серверная части размещаются в одном проекте.

### Версии для первой сборки

- Нижняя граница установки — Android 12 (`minSdk = 31`). Проверенная сборка использует JDK 17, Android SDK 36, Android Gradle Plugin 8.13.2, Gradle 8.13 через Wrapper, Kotlin 2.3.21 и Compose BOM `2026.04.01`. Версии Room и WorkManager закрепляются при их подключении.
- Серверный каркас проверен на Python 3.13 и PostgreSQL 17 в Docker Compose. Версии FastAPI, Pydantic и SQLAlchemy закреплены в `server/uv.lock`. Alembic подключается на шаге 1.2.
- Сборка, запуск и обновление тестового APK проверены на одном Huawei P60. [Результаты запуска и проверки](../plans/1.1-environment.md#прогресс-и-ближайшее-действие)

## Границы компонентов

- Android-интерфейс отвечает за отображение и действия пользователя.
- Прикладная логика определяет согласованные правила записей, покупок и дел, независимо от экранов и внешних SDK.
- Локальная база хранит данные, доступные приложению без сети.
- Обмен с сервером обновляет локальную копию данных; пользовательские изменения отправляются непосредственно серверу без очереди офлайн-изменений.
- Серверный API проверяет доступ, обрабатывает операции и сохраняет общее состояние в PostgreSQL.

Начальная серверная часть — одно приложение. Дополнительные сервисы и архитектурные слои вводятся при реальной необходимости. Общее поведение и права определены в [PRODUCT.md](PRODUCT.md), а не выбранными библиотеками.

## Структура проекта

Сервер — одно приложение FastAPI в `server/`. Android — один Gradle-модуль `:app` в `android/`. Функции разделяются пакетами внутри приложений. Карта показывает расположение файлов по мере реализации. Каталоги создаются, когда появляются файлы для текущего шага.

```text
rutina/
├── Makefile
├── compose.yaml
├── compose.local.yaml
├── compose.test.yaml              # изолированная PostgreSQL для интеграционных тестов
├── compose.prod.yaml              # при подготовке рабочей выкладки
├── .env.example
├── server/
│   ├── Dockerfile
│   ├── pyproject.toml
│   ├── uv.lock
│   ├── src/rutina/
│   │   ├── main.py                # сборка FastAPI и регистрация роутеров
│   │   ├── config.py              # типизированные настройки
│   │   ├── errors.py              # базовое исключение приложения
│   │   ├── observability.py       # настройка логирования и контекст запроса
│   │   ├── db/
│   │   │   ├── session.py         # подключение и сессии SQLAlchemy
│   │   │   └── queries/           # запросы по областям: health.py, purchases.py и другие
│   │   └── features/              # health, затем auth, homes, purchases
│   ├── migrations/                # Alembic с шага 1.2
│   └── tests/                     # unit, integration, общие фикстуры
├── android/
│   ├── gradle/                    # Wrapper и libs.versions.toml
│   └── app/src/
│       ├── main/kotlin/<пакет>/
│       │   ├── app/               # запуск, навигация и сборка зависимостей
│       │   ├── core/              # общий HTTP-клиент, позже подключение Room
│       │   └── feature/           # connection, затем auth и purchases
│       ├── main/res/              # ресурсы, в том числе values и values-ru
│       ├── test/                  # тесты на JVM
│       └── androidTest/           # тесты, которым нужна среда Android
├── docs/
└── plans/
```

### Сервер

Код функции размещается в `server/src/rutina/features/<функция>/`. Использовать пример ниже как схему размещения. Создавать файл, когда в пакете появляется соответствующая ответственность.

- Запросы на чтение и запись размещаются в `server/src/rutina/db/queries/`, по одному файлу на предметную область по мере необходимости. Например, проверка связи с БД живёт в `health.py`, запросы покупок — в `purchases.py`. `queries/__init__.py` остаётся пустым. Сервисы импортируют из конкретного файла, например `from rutina.db.queries.purchases import list_purchases_by_task`.
- `main.py` собирает приложение, подключает роутеры и обработчики ошибок. `db/session.py` предоставляет подключение и сессии, независимо от предметных пакетов.

#### Пример пакета purchases

- **`router.py`** — объявляет HTTP-роуты. Принимает запрос, получает зависимости через DI, вызывает одну операцию и формирует ответ.
- **`schemas.py`** — модели Pydantic для запросов и ответов API.
- **`service.py`** — операции добавления и получения покупок. Проверяет доступ к дому, применяет правила и управляет транзакцией.
- **`models.py`** — ORM-модели таблиц покупок.
- **`types.py`** — типы прикладного слоя, например тип результата операции и `PurchaseStatus`, когда он понадобится. Статус объявляется здесь один раз и используется в ORM, запросах и API.
- **`errors.py`** — исключения покупок, если они нужны. Наследуются от общего `AppError`.

При сохранении покупки `features/purchases/router.py` вызывает операцию из `features/purchases/service.py`, которая использует `db/queries/purchases.py`. [Правило тонких роутов](CODING_STANDARDS.md#слои-и-зависимости)

### Android

- Код функции размещается в `feature/<функция>/` внутри основного Kotlin-пакета. В `ui/` живут Compose, `ViewModel` и состояние экрана. В `data/` живут обращения к API и Room по этой функции. Источник статусов, общих с сервером, — контракт API. [Правила типизации](CODING_STANDARDS.md#типы-и-статусы)
- `app/` собирает зависимости и навигацию, включая описание общей базы Room с таблицами и DAO функциональных пакетов. `core/` содержит общую инфраструктуру. Например, пакет покупок использует общий HTTP-клиент и получает DAO покупок при сборке зависимостей. Запросы и преобразования для покупок остаются в пакете покупок.

### Правила размещения

- На сервере роут вызывает прикладную операцию, а та использует запросы из `db/queries/`. Модуль запросов может импортировать сессию, ORM-модели и типы, включая enum. Импорты роутов и сервисов из слоя запросов запрещены. Модули моделей и типов, которые использует слой запросов, сами не импортируют запросы, сервисы или роуты.
- Один запрос может использоваться несколькими сервисами. Каждый прикладной сценарий сохраняет необходимые проверки прав и управляет своей транзакцией. Если нужно переиспользовать бизнес-правило или действие целиком, вызывать типизированную прикладную операцию с явной зависимостью. Зависимости между сервисами должны быть однонаправленными.
- Код функции размещать у её владельца по этой схеме. Общая инфраструктура `core/` на Android не зависит от функциональных пакетов.
- Новый корневой каталог или Gradle-модуль требует обоснования потребностью текущего этапа. При изменении структуры актуализировать этот раздел. Порядок появления кода определяет [основной план](../plans/MASTER_PLAN.md), включая [подплан каркаса](../plans/1.1-environment.md).

## Android и работа без сети

Сервер хранит общее подтверждённое состояние дома, Room — локальную копию для отображения и чтения без сети. Все изменения требуют доступного API и подтверждения сервера; очереди отложенных офлайн-изменений нет. Продуктовые решения B07 закреплены в [PRODUCT.md](PRODUCT.md#работа-без-сети); схема хранения, API и код ещё не созданы.

### Версии и согласованное применение изменений

Редактирование передаёт ожидаемую версию всей записи. Проверка версии и запись новой версии выполняются атомарно; разделять их на независимые проверку и сохранение нельзя. Длительной блокировки на время заполнения формы нет. Блокировки БД ограничены выполнением серверной транзакции. Проверка охватывает запись целиком, без автоматического объединения разных полей или перезаписи устаревшим запросом.

Сервер сохраняет связанные эффекты согласованно: состояние покупки и её расход, единственный возврат покупки и его допустимую сумму, выполнение дела и единственное следующее повторение, покупку и её связь с делом. Версии и ограничения применяются также к изменению связей. Права, статус участника, дом, наличие объектов и финансовые ограничения проверяются при обработке запроса, включая конкурентные запросы. Общее заполнение ориентиров и остановка расписания должны проверять актуальность затрагиваемых записей и подтверждённого набора; точное представление версий и условий операции выбрать перед реализацией.

Одинаковая отметка покупки с той же суммой/датой или выполнения повторяющегося дела с той же фактической датой, без других правок, не применяется второй раз. Возвращается понятный результат «уже отмечено» и актуальные данные; первая отметка дела сохраняет участника и техническое время. Различия и дополнительные правки проходят обычную проверку версии. Независимые реальные возвраты или покупки не объединяются по одному совпадению суммы и даты.

Оплата и остановка расписания, исправление даты выполнения и снятие отметки обрабатываются по [продуктовым правилам](PRODUCT.md#одновременные-изменения) в согласованной транзакции. Если оплата будущего платежа за выбранной конечной датой принята первой, остановка или сокращение отклоняются. При другом изменении списка исключения без блокирующей оплаты требуется новое подтверждение. Уже исключённый платёж не восстанавливается оплатой. Автоматический пересчёт или удаление следующего дела допускаются, пока его поля не меняли вручную и его не выполнили. Связи с покупками этому не препятствуют. При проверке допустимости пересчёта различать ручные правки полей дела и изменения связей, даже если проверка конфликтов учитывает оба вида изменений. При пересчёте меняется дата дела, при удалении дела его связи убираются в той же транзакции, а покупки и их данные сохраняются. Конкурентная привязка после удаления отклоняется.

### Повторы запросов и ошибки

У одного пользовательского действия должна сохраняться идентичность при проверке результата и повторной отправке. Принятое действие не исполняется заново при потере ответа; идентичные параметры разных самостоятельных действий сами по себе не делают их одним действием. Защита от повторов и сохранение результата согласованы с бизнес-транзакцией. Формат идентификатора, способ проверки результата, хранение подтверждений и срок их хранения определить при первом API записи в 1.3. Контракт должен различать безопасный повтор исходного действия и случай, когда результат уже нельзя установить. В последнем случае сервер отклоняет повтор без выполнения записи и сообщает об этом клиенту. Поведение формы определено в [PRODUCT.md](PRODUCT.md#ошибки-и-неизвестный-результат). Идентификатор и проверка нужны для исходного действия в открытой форме. После закрытия приложения клиент использует обычное обновление B07 при следующем запуске. Он не восстанавливает проверку исходного действия и не отправляет изменение повторно.

Ошибки связи, конфликт версии, удаление объекта, отказ в доступе и неизвестный результат запроса различаются. Открытая форма сохраняет ввод для предусмотренных действий интерфейса; при потере ответа проверяется исходное действие и при необходимости повторяется именно оно. Это восстановление запроса из открытой формы, без фоновой офлайн-очереди. Проверка прав обязательна и при возврате ранее сохранённого результата: повтор не должен раскрыть содержимое отключённому участнику. Создание новой записи на основе ввода после удаления возможно только явным отдельным действием с обычными проверками.

### Локальные данные и отключение участника

Получив сведения об отключении, клиент скрывает семейное содержимое, блокирует изменения и отменяет локальные напоминания; локальную копию автоматически не удаляет. Повторное включение требует подтверждённого доступа и обновления данных перед показом. До получения отключения телефон без связи продолжает чтение копии и локальные напоминания. Срок офлайн-доступа и отдельные обязательные периодические проверки доступа не вводятся. Сервер проверяет активность при каждом обращении независимо от состояния клиента.

### Экономное обновление локальной копии

Обновление запускается при открытии/возвращении приложения, входе в раздел, вручную и после сохранения для затронутых данных. Совпавшие поводы объединяются; одинаковые запросы не выполняются параллельно. Достаточный ответ сохранения применяется к локальной копии без лишней загрузки. На неподвижном открытом экране постоянного опроса нет. Фоновое получение изменений выполняется через WorkManager с учётом сети и ограничений Android; обязательного срока в минутах и мгновенной доставки нет. Частоту и параметры повторов выбрать перед реализацией и проверить на Huawei P60. После ошибок интервалы повторов увеличиваются; отдельные запросы проверки доступности не нужны.

Первичная загрузка создаёт локальную копию; последующие обновления передают изменения и удаления, а при их отсутствии небольшой ответ без повторной передачи записей. Способ отслеживания изменений, удаления из копии и восстановления обмена после потери его состояния определить в подплане 2.2. Первый сквозной сценарий использует ручную загрузку покупок в 1.3 и сохранение загруженных записей для чтения из Room в 1.4. По B08.1 корзины и восстановления записей в MVP нет; технические метки удаления для обмена допустимы и не хранят содержимое для пользовательского восстановления. По B08.2 пользовательской истории правок нет; проверка версии B07 сохраняется.

Время успешного обновления относится к полученным отображаемым данным, включая подтверждённый ответ об отсутствии изменений. Оно не меняется после ошибки или одной отправки правки. Частичная загрузка не должна изображаться обновлением всей копии. При недоступном API остаются прежние данные в пределах прав и сообщение об ошибке. Замерять число запросов и переданные байты при отсутствии изменений, правке одной записи и длительной фоновой работе; полную базу при каждом открытии не загружать.

WorkManager не гарантирует точное время календарного уведомления.

### Хранение данных на телефоне

Сроки и состояния определены в [PRODUCT.md](PRODUCT.md#хранение-данных-на-телефоне). Обмен обновляет актуальные записи и недавние завершённые данные. Для более старых периодов нужна загрузка по запросу и учёт времени последнего просмотра. При успешном обновлении удалять из Room записи за пределами локального срока хранения с учётом загруженных периодов и связей, нужных для отображения. Очистка Room не отправляет удаления на сервер. Границы календарных месяцев определяются по времени дома.

Клиент должен различать полный загруженный период и частичную выборку, в том числе когда часть периода удалена или в периоде нет записей. Обновление, очистка и учёт полноты должны давать согласованный результат. Текущий остаток должен учитывать все подтверждённые финансовые операции, включая те, подробности которых не хранятся локально. Способ обмена остатком и учёта полноты определить при подготовке API. Правило полноты загруженного плана распространяется на статусы его платежей. При очистке истории расходов сохранять данные, необходимые для показа досрочно оплаченного повторения и отмены его напоминания, даже если подробности расхода больше не хранятся локально.

Обычное обновление APK сохраняет сессию и Room, в том числе при изменениях схемы через миграции. После удаления приложения или очистки его данных следующий запуск требует входа и первой загрузки. Конфигурация резервирования и переноса данных Android должна исключать автоматический возврат прежней локальной копии и сведений о входе после переустановки.

Когда сервер подтверждает истечение сессии или её недействительность после сброса пароля, скрыть семейные данные и отменить локальные напоминания. Показ копии и восстановление актуальных напоминаний разрешены после нового входа и успешного обновления. При обычной ошибке связи действуют правила обновления B07. Постоянное хранение ввода формы для восстановления после закрытия приложения в MVP не предусмотрено.

## Сервер, API и права

- Телефон обращается к API, а не напрямую к PostgreSQL. В APK не размещаются серверные секреты и пароль БД.
- Аутентификация устанавливает учётную запись; доступ к конкретному дому и операции проверяется отдельно.
- Проверки распространяются на создание, просмотр, списки, исправления, удаление, отметки выполнения и обмен изменениями.
- Техническая роль управляющего не должна обходить членство в доме при чтении его семейных записей.
- Одна учётная запись связана с одним домом. В доме может быть несколько участников. Ровно один участник является администратором. Эти ограничения нужно учитывать при подключении и проверке членства.
- При приглашении члена семьи в приложение сервер проверяет, зарегистрирована ли почта. Если зарегистрирована, отклоняет подключение нового пользователя; приложение показывает согласованное сообщение из PRODUCT.md красным. Не создавать дубликат, не присоединять существующую учётную запись и не переносить её между домами. Повторное включение участника своего дома остаётся отдельным действием.
- Отключение участника представляется неактивным статусом, а не удалением его учётной записи или семейных записей. Ссылки на автора и исполнителей сохраняются там, где они предусмотрены (дела и заметки); получатели покупок сохраняются независимо от доступа к приложению. Администратор может вернуть участнику активный статус в том же доме без новой регистрации, смены пароля или создания дублирующей учётной записи. Проверки прав и обмен учитывают статус по B07.4: после получения отключения клиент скрывает семейные данные и отменяет напоминания, локальную копию автоматически не удаляет; без связи ограничения применяются после получения отключения.
- Авторство дел и заметок и исполнитель отметки дела — разные сведения; клиент не назначает себе чужое авторство или права. Для покупок и финансовых операций продуктового авторства и привязки к подтвердившему участнику нет. Аутентификация и серверные проверки прав остаются обязательными; получатель покупки — отдельная связь, а не автор.
- Любой участник дома может исправлять любые общие доходы, расходы, покупки, дела, заметки и категории независимо от автора, а также ставить и снимать отметки выполнения или покупки. Сервер не ограничивает исправления авторством; для дел сохраняет предусмотренные сведения об авторе и исполнителе отметки. Для финансов проверяет связи, суммы и допустимость перехода состояния. Правило хранения текущего состояния и сведений об авторстве закреплено в [B08.2](PRODUCT.md#удаление-история-и-резервные-копии).
- Удалять общие записи и неиспользуемые категории может только администратор. Интерфейс требует явного подтверждения перед удалением; отказ от подтверждения не отправляет действие удаления. Сервер независимо проверяет роль и ограничения целостности. Ограничения удаления описаны в [правилах карточек семьи](PRODUCT.md#члены-семьи-и-доступ-к-приложению), [категорий](PRODUCT.md#финансы) и [удаления записей](PRODUCT.md#удаление-история-и-резервные-копии).
- Остановка и сокращение расписания платежей доступны любому участнику с подтверждением затрагиваемого будущего плана. Сервер проверяет принадлежность расписания и платежей дому, допустимость новой даты и список исключения по [правилам окончания](PRODUCT.md#просрочка-изменения-и-окончание). Сервер запрещает удаление отдельного платежа расписания даже администратору.
- Сервер проверяет завершение [первичной настройки дома](PRODUCT.md#финансы) перед доступом к основным разделам и отправкой приглашений. До настройки администратору доступны ввод остатка и ведение карточек семьи. Первое сохранение остатка и даты начала учёта выполняется атомарно. При одновременном вводе на двух телефонах принимается только одно первое сохранение.
- Все пользовательские изменения требуют доступного API и проверяются сервером при обработке. Открытая форма и локальная копия не дают разрешения на действие; права и действительность сессии могли измениться после загрузки данных.

FastAPI формирует обязательный контракт OpenAPI и Swagger UI. Типы клиента проверяются по [правилам типизации](CODING_STANDARDS.md#типы-и-статусы). Android игнорирует новые необязательные поля. Если неизвестное значение меняет смысл записи, клиент сообщает о несовместимости и сохраняет последнюю успешно загруженную копию.

Выбрана схема подключения по одноразовой ссылке-приглашению на почту. Участник открывает приглашение в приложении, вводит отображаемое имя и самостоятельно задаёт пароль. Для последующих входов используются почта и пароль. Постоянные пароли не рассылаются по почте, приглашение не заменяет пароль при последующих входах. В MVP приглашение не истекает по времени; ограничение срока прорабатывается после MVP по D05.

Администратор своего дома может отменить непринятое приглашение либо отправить его заново на ту же почту. Сервер после отмены не принимает старую ссылку; при повторной отправке выдаёт новую и делает предыдущую недействительной. Временной срок действия не вводится. Проверка актуальности и использования выполняется на сервере при подтверждении подключения. Эти действия не предназначены для повторной регистрации уже подключённой учётной записи.

Смена почты, пользовательский выход и экран управления устройствами исключены из MVP и вынесены в [C02](COMMERCIAL_RELEASE_QUESTIONS.md#c02-смена-почты-выход-и-управление-устройствами). Вход сохраняется между обычными запусками приложения и после перезагрузки телефона. Сервер выдаёт случайный токен сессии и хранит его хеш. Android хранит токен в защищённом хранилище. Сессия действует 90 дней с момента входа, без автоматического продления. Сервер проверяет действительность сессии и статус участника. При подтверждённом сервером истечении сессии и при отсутствии связи действуют [продуктовые правила локальной копии](PRODUCT.md#хранение-данных-на-телефоне).

Согласован сброс пароля через отправку ссылки на зарегистрированную почту владельца. Администратор запрашивает отправку для участника своего дома; управляющий отправляет ссылку администратору через серверную CLI. Используется общий механизм выдачи и проверки ссылки, а не отдельные правила смены пароля для CLI. Владелец сам задаёт новый пароль; отправляющий не узнаёт его и не получает доступа к содержимому дома. Название CLI-команды и реализация пока не определены.

Ссылка сброса пароля действует 30 минут с момента выдачи и принимается только один раз. Отправка и открытие ссылки сами по себе не меняют учётную запись и сессии. После успешного подтверждения нового пароля все прежние сессии этой учётной записи аннулируются сервером; требуется вход с новым паролем на каждом устройстве. Нельзя считать задачу решённой только закрытием экранов на одном телефоне. Проверка неизвестного результата из открытой формы определена в B07; последствия сброса для локальной копии, незавершённого ввода и восстановления результата после закрытия остаются в B08; сброс пароля не является их удалением. Очереди офлайн-записей в MVP нет.

Срок ссылки сброса не применяется к приглашениям: они в MVP не истекают по времени. Если одновременно забыты пароль и доступ к почте, сначала восстанавливается почтовый ящик у почтового сервиса. В MVP нет обходного сброса или смены адреса, в том числе через CLI; эта команда отправляет ссылку только на зарегистрированную почту. При известном пароле вход не требует доступа к почтовому ящику, но проверки сессии и статуса участника сохраняются. Альтернативное восстановление вынесено в [C03](COMMERCIAL_RELEASE_QUESTIONS.md#c03-восстановление-без-доступа-к-почте).

Android сохраняет идентификатор привязанной учётной записи независимо от токена. При повторном входе клиент сверяет серверный идентификатор аккаунта с сохранённым до сохранения токена и загрузки данных. При несовпадении привязка, локальная копия и состояние доступа прежнего аккаунта сохраняются. [Правило повторного входа](PRODUCT.md#дома-и-учётные-записи)

### Карточки членов семьи и доступ

Карточка члена семьи (человек или питомец) принадлежит дому и существует независимо от учётной записи. Администратор формирует состав семьи; его собственная карточка присутствует сразу. Приглашение и подключение связываются с выбранной карточкой без создания второго получателя. Учётная запись, карточка и приглашение проверяются на принадлежность одному дому; прежние правила уникальности почты, одноразовости и проверки доступа сохраняются.

Получатель покупки — «Семья» либо ссылка на карточку своего дома. Наличие карточки не даёт прав входа или доступа к API. Создание и управление составом семьи остаются административными действиями; управляющий приложением создаёт дом и назначает администратора, не получая доступа к семейным данным.

При удалении карточки сервер проверяет [использование карточки и действующие приглашения](PRODUCT.md#члены-семьи-и-доступ-к-приложению). Проверки и ограничения целостности должны защищать связи и при конкурентном создании связи или приглашения. Проверку каждого вида связи добавлять вместе с соответствующей функциональностью.

### Приглашение из письма в приложение

Согласовано дополнительное поле отображаемого имени при подключении. Идентичность участника и авторство не должны определяться отображаемым именем; это представление учётной записи для семьи, а не подтверждение права доступа.

Ссылка из письма должна позволять перейти к экрану приглашения в установленном приложении. Технический кандидат для поддерживаемых устройств — HTTPS-ссылка с Android App Links: связь домена и приложения подтверждается файлом `/.well-known/assetlinks.json`, идентификатором приложения и отпечатком сертификата подписи APK. Наличие приложения, проверка домена, настройки устройства и поведение почтового клиента влияют на переход.

[Android Developers](https://developer.android.com/training/app-links) указывает поддержку Android App Links на устройствах с Google-сервисами. Для Huawei P60 без них автоматическая верификация остаётся неподтверждённой. В 5.1 проверить основной переход из почтового клиента на целевом устройстве до выбора механизма. Если переход через App Links не работает, согласовать способ основного открытия приглашения до реализации зависимого сценария. Пользователь устанавливает APK самостоятельно. Дополнительные способы подключения вынесены в [D04](DEFERRED_QUESTIONS.md#d04-установка-приложения-и-запасные-способы-принятия-приглашения).

Если APK не установлен, пользователь устанавливает его самостоятельно до принятия приглашения. Служебная страница установки, сценарий письма на ПК и ручная вставка приглашения отложены на проработку после MVP по D04. Не обещать автоматический перенос приглашения через установку приложения.

Переход передаёт данные приглашения приложению, но сервер проверяет его действительность, адресата, факт предыдущего использования, отмену и замену новой ссылкой перед подтверждением доступа. В MVP нет проверки истечения по времени и фонового механизма истечения приглашений; это [D05 после MVP](DEFERRED_QUESTIONS.md#d05-ограничение-срока-действия-приглашения). Открытие ссылки или предпросмотр письма не должны сами по себе активировать учётную запись или расходовать приглашение. Приглашения не помещать в логи и примеры как реальные токены.

Перед показом формы принятия Android проверяет, связан ли клиент с другим аккаунтом, с учётом сохранённой привязки при истёкшей сессии или скрытой локальной копии. На таком клиенте форма недоступна, запрос принятия не отправляется и состояние прежнего аккаунта не меняется. Проверка действительности приглашения и прав доступа остаётся на сервере. [Правила приглашения](PRODUCT.md#дома-и-учётные-записи)

Локально обработку входящей ссылки можно проверять средствами Android SDK. Для проверки полного сценария App Links потребуется доступный телефону HTTPS-домен и настройка связи с подписью APK; адрес локального API сам по себе не обеспечивает проверку домена. Развёртывание такой среды требует отдельного разрешения. На целевом Huawei проверить почтовый клиент, браузер и основной переход в установленный APK; проверку запасных путей выполнять после их проработки после MVP.

## Финансовые данные

Продуктовые правила B03–B04 закреплены в [PRODUCT.md](PRODUCT.md#финансы): один общий бюджет дома в RUB, начальный остаток, доходы, расходы и отдельные возвраты без счетов и переводов между ними.

Для точного хранения денежных значений использовать целое количество копеек, без двоичной арифметики с плавающей точкой. Точность — одна копейка (два десятичных знака рубля); локальное хранилище, API и сервер должны сохранять сумму без потерь. Конкретные поля и диапазоны определить при подготовке схемы и контракта API. Язык интерфейса не меняет валюту бюджета.

Разделять дату финансовой операции и техническое время её создания или изменения. Итоги периода рассчитываются по дате операции, в том числе для внесённых позднее записей. Текущий остаток не сбрасывается на границе месяца. Возврат увеличивает остаток и уменьшает расходы, не попадая в доходы; исходная покупка сохраняется. Повторная синхронизация не должна повторно влиять на итоги. Единый часовой пояс дома определяет «сегодня» и границы семейных календарных дней по B06; пояс телефона не меняет даты операций и семейное расписание.

Категория принадлежит дому, иерархия ограничена двумя уровнями. Сервер проверяет дом, права и глубину при создании и изменении; локальная модель сохраняет подтверждённые связи и ограничения. Создавать и редактировать категории может любой участник, удалять — только администратор после подтверждения. При удалении категории применять [продуктовые ограничения](PRODUCT.md#финансы). Ссылки из расписаний проверять с момента появления расписаний. Проверки должны исключать нарушение связей и при конкурентных запросах. Не заменять отказ каскадным удалением содержимого, очисткой категории или архивированием. Изменения требуют доступного сервера по B07.1; применяются правила конфликтов B07.2.

Начальный остаток хранится один раз на дом вместе с датой начала учёта. Сервер определяет эту дату при первом сохранении по часовому поясу дома и сохраняет её при исправлении суммы. Сервер допускает ввод и исправление только администратором дома. Для покупок и доходов сервер проверяет, что фактическая дата не раньше начала учёта.

### Покупка и учёт расхода

Все расходы представлены покупками товаров, услуг или платежей. Запланированная и купленная покупка — одна предметная запись с одними категориями и одним полем цены. Пользовательского ввода отдельного расхода и привязки ранее созданного расхода к покупке нет. Повторяющиеся платежи используют эту же модель по завершённому B05; границы расписания и отдельных платежей описаны ниже.

До подтверждения цена необязательна и не влияет на бюджет; пустое значение отличается от нуля. Подтверждение заменяет ориентир фактической ценой, задаёт фактическую дату и автоматически учитывает расход. Покупка и её финансовый результат сохраняются согласованно; повторный запрос или синхронизация не создают второй расход. Купленная вещь за 0 ₽ не меняет остаток и не создаёт доход. Отдельно удалить финансовый результат, оставив покупку купленной, нельзя. Конкретная схема хранения и контракт API пока не выбраны.

Получатель по умолчанию — «Семья», иначе карточка члена этого же дома. Авторство финансовых операций и покупок и привязка к создавшему или подтвердившему участнику не требуются; это не отменяет аутентификации. Получатель не является личным счётом и не меняет общий бюджет.

Крайний срок запланированной покупки хранится отдельно по смыслу от фактической даты и технического времени. При снятии ошибочной отметки «Куплено» без возвратов расход исключается, цена остаётся ориентиром, фактическая дата очищается, прежний крайний срок сохраняется. Удаление ошибочной купленной покупки без возвратов разрешено только администратору после подтверждения и также исключает расход. Исправления отражаются в остатке и затронутых периодах. Показ за 3 дня и тихое уведомление за 2 дня определены в [правилах дат и напоминаний](#даты-дела-и-напоминания).

### Расписания и очередные платежи

Продуктовые правила B05 закреплены в [PRODUCT.md](PRODUCT.md#обязательные-платежи). Расписание повторяющейся покупки отделяется от её отдельных платежей. Периодичность — параметр расписания («ежемесячно» или «ежегодно»); отдельный пользовательский справочник периодичностей не нужен. Расписание задаёт первый платёж, исходные число и месяц, необязательный последний платёж, общие параметры покупки и общий ориентир суммы.

Календарь и сводка должны показывать обязательства за выбранные месяц и год, включая будущие периоды, без ручного создания каждого повторения. Конкретный способ расчёта будущего плана и момент сохранения отдельных покупок определить при подготовке схемы и API; открытие экрана не должно становиться условием существования обязательства. Не создавать бесконечный набор будущих записей заранее.

При материализации очередной покупки нужна устойчивая связь с расписанием и соответствующим повторением. Повторное открытие периода, повтор запроса, два телефона и последующая синхронизация не должны создавать вторую покупку или второй расход. Индивидуальное изменение срока или фактической даты не должно терять идентичность повторения. Конкретные ключи, ограничения уникальности и транзакции выбрать перед реализацией; согласованные правила конфликтов B07 сохраняются.

Даты повторений рассчитываются из исходных параметров расписания: короткий месяц временно использует свой последний день, без сдвига исходного числа следующих повторений. Признак «Просрочен» определяется по прошедшему сроку и отсутствию оплаты; он не добавляет третье состояние покупки и не переносит её автоматически. Признак просрочки и определение «сегодня» используют единый часовой пояс дома по B06.

У каждого платежа одно текущее поле цены. Сумма из соответствующей прошлогодней оплаты копируется в новый ориентир, при её отсутствии используется общий ориентир расписания. Если оба источника отсутствуют, подстановка сохраняет текущее значение платежа. Источник относится к соответствующему повторению, а не случайной операции с совпавшим месяцем фактической оплаты. Копия не пересчитывается вслед за исправлением источника. Заполнение ориентиром и подстановка прошлогодних фактических сумм затрагивают все неоплаченные платежи выбранного года, включая просроченные. Перед заменой ручных сумм требуется одно подтверждение на всю операцию. Текущий общий ориентир меняется в расписании. Подтверждение оплаты заменяет ориентир фактом без сохранения второй цены; стоимость за 0 ₽ и пустое значение различаются.

Исправления отдельного платежа отделяются от изменения расписания с выбранного месяца. Изменение расписания касается будущих неоплаченных платежей, сохраняет оплаченные и просроченные, а также индивидуальные поправки без явного согласия на замену. Окончание расписания исключает будущие неоплаченные повторения после конечной даты из плана и его сумм; сохранность оплаченных, включая оплаченные заранее, возвратов и просроченных обязательна. Предварительный просмотр и сохранение новой даты окончания проверяют оплаченные платежи, срок которых позже и новой конечной даты, и текущей даты дома. При сохранении проверка и изменение расписания выполняются в одной транзакции с учётом конкурентной оплаты. При подтверждении оплаты сервер проверяет срок платежа по дате дома и требует явного подтверждения для будущего платежа. Повторный расчёт календаря и синхронизация должны сохранять результат исключения по условиям на момент подтверждения. Исключённое повторение не становится просроченным после перехода через его прежнюю дату. Отдельное исключение одного повторения в MVP не предусмотрено.

Прогноз обязательств за месяц/год использует текущие ориентиры неоплаченных платежей и отделён от фактических расходов и денежного остатка. Пустая сумма не становится нулевой. Отдельного банковского остатка долга и расчёта процентов нет. Схема данных и контракт API пока не реализованы. Изменения расписаний требуют доступного сервера, отложенная отправка без сети исключена из MVP; права, повторные запросы и согласованность плана проверяются на сервере, правила конфликтов определены в B07.2.

### Покупки, возвраты и целостность

Полный или частичный возврат — отдельная связанная запись по дате получения денег. Возврат уменьшает расходы, увеличивает остаток и не попадает в доходы. Исходная покупка остаётся купленной, каждый финансовый результат учитывается один раз. Сервер допускает одну запись возврата на покупку, в том числе при одновременных запросах. Предлагаемая по умолчанию сумма — вся стоимость покупки. Сервер проверяет [границы суммы и даты возврата](PRODUCT.md#возвраты-денег) при создании и исправлении возврата, а также при изменении цены или фактической даты покупки.

Категория и получатель возврата определяются покупкой, отдельного выбора нет. Их исправление у покупки должно отражаться и для её возврата без изменения его даты. Технический способ наследования выбрать при подготовке схемы; не допускать расхождения классификации покупки и возвратов.

Сервер запрещает снятие «Куплено» и удаление покупки с возвратами. Редактирование возврата доступно любому участнику; удаление ошибочного возврата — администратору после подтверждения, с пересчётом остатка и периода возврата без удаления покупки. Проверки сумм, прав и наличия связей должны быть согласованными и устойчивыми к конкурентному созданию возврата, исправлению стоимости, снятию отметки и удалению. Локальная проверка формы не заменяет серверную; подтверждённый результат применяется к локальной копии. Схему транзакций и протокол конфликтов определить перед реализацией по B07.

### Динамические отчёты

Отчёт за месяц, год или выбранный период рассчитывается по актуальным записям и фильтрам категорий, подкатегорий и получателей («Семья» или конкретный член семьи), включая их сочетания. Источник — записи БД, а не статичные снимки итогов. Покупки относятся к периоду по фактической дате, возвраты — по дате получения денег. Изменения суммы, даты, категории и получателя отражаются в соответствующих отчётах; запланированные покупки исключены, двойной учёт недопустим.

При открытии отчёта и смене фильтров выполнять новый расчёт. При доступном сервере использовать актуальные исходные данные, без связи использовать локальные только при полном покрытии выбранного периода и показывать время их обновления. При неполном покрытии требуется связь. Семидневный срок B08.4 относится к исходным записям старого периода. Сервер проверяет дом при выборках и расчётах. Экспорт отчётов, персональные счета и новые аналитические показатели не входят в это решение.

## Локальная разработка и будущий сервер

### Docker Compose

- Корневой `compose.yaml` задаёт общие сервисы API и PostgreSQL, внутреннюю сеть и именованный том БД. PostgreSQL доступна внутри сети Compose. Для проверки готовности PostgreSQL задан стартовый период в три минуты. API запускается после готовности БД. `GET /health` ограничивает ожидание всей проверки связи с БД тремя секундами.
- `compose.local.yaml` добавляет локальную публикацию API. Обычный запуск использует `127.0.0.1:8000`. Для проверки на Huawei явно задаётся LAN-адрес компьютера. Локальные настройки и вымышленные секреты хранятся в `.env` вне Git, список параметров — в `.env.example`. При исчерпании пула Docker локальную подсеть можно задать в `compose.local.network.yaml` вне Git. Для тестов используется отдельная одноразовая PostgreSQL. Локальному и рабочему запуску задаются разные имена проектов Compose, чтобы разнести сети и тома.
- Перед рабочей выкладкой добавить `compose.prod.yaml` и явно запускать его вместе с `compose.yaml`. Использовать версионированный образ API, собранный из того же `server/Dockerfile` и `uv.lock`. Рабочие настройки и секреты подаются извне, том БД относится к рабочему проекту Compose. Доступ из приложения идёт через HTTPS. Хостинг, домен, прокси и способ доставки образа выбираются при подготовке выкладки.
- Миграции Alembic с шага 1.2 запускаются отдельной командой с явно выбранной средой. Перед рабочей выкладкой описать порядок применения миграций, проверку `/health` по HTTPS и порядок возврата версии API с учётом совместимости схемы. Настройка рабочего HTTPS, технического доступа, почты и выкладка выполняются по отдельным поручениям. Резервное копирование и пробное восстановление должны быть готовы до ввода реальных семейных данных по [D07](DEFERRED_QUESTIONS.md#d07-резервное-копирование-перед-семейным-запуском).

### Команды разработки

Корневой `Makefile` предоставляет короткие команды для локальной работы. `make help` показывает доступные цели. `make up`, `make down`, `make status` и `make logs` управляют локальным Compose. `make down` сохраняет том PostgreSQL. `make fmt` форматирует код, `make check` запускает линтеры, проверку форматирования и типизацию Python, `make test` запускает тесты, `make apk` собирает отладочный APK через Gradle Wrapper. Команды добавляются вместе с поддерживаемыми сценариями. При изменении штатных команд обновлять `Makefile` и [README.md](../README.md).

### Данные для разработки и проверок

Тесты и локальная разработка используют только воспроизводимые вымышленные данные. При реализации приглашений тестовую отправку и содержимое письма проверять в локальном почтовом сервисе без отправки наружу, обработку входящей ссылки — на APK. Полный переход из почтового клиента через проверенный Android App Link требует отдельно настроенного HTTPS-домена. Первый сквозной сценарий использует заранее подготовленные учётные записи.

Семейные записи в личном MVP хранятся в PostgreSQL без прикладного шифрования. К выбору схемы защиты для других семей вернуться по [D09](DEFERRED_QUESTIONS.md#d09-шифрование-данных-при-подключении-других-семей).

### Резервное копирование перед семейным запуском

Правила B08.3 согласованы как простая страховка. Разработку и настройку выполнять по отдельному поручению перед вводом реальных семейных данных; см. [D07](DEFERRED_QUESTIONS.md#d07-резервное-копирование-перед-семейным-запуском). Сейчас копирование не реализовано и Яндекс Диск не подключён.

- Раз в сутки cron на сервере запускает отдельный скрипт: `pg_dump` создаёт копию схемы и данных PostgreSQL, файл сжимается, шифруется и загружается в отдельную закрытую папку Яндекс Диска владельца. Android-приложение и FastAPI расписанием не управляют. Точное время выбрать при настройке.
- Копируется вся серверная база, включая все её дома и учётные записи. APK, исходный код и несохранённый ввод телефона в эту копию не входят. Доступ к файлам имеет владелец сервера; пользовательская роль управляющего не получает через приложение доступ к чужим домам.
- Срок хранения — 14 дней. Очистка касается только файлов этого резервирования в выделенной папке и выполняется после успешной загрузки новой копии. Ошибка создания или отправки записывается в журнал без секретов и содержимого базы; прежние успешные копии сохраняются. Отдельный сервис, сложный мониторинг и непрерывное восстановление по журналам БД не требуются.
- Токен Диска и ключ шифрования хранятся вне репозитория; дополнительный экземпляр ключа сохраняется у владельца отдельно от сервера. На Диск отправляются только зашифрованные файлы.
- Восстановление выполняется владельцем сервера вручную. При настройке один раз проверить скачивание, расшифровку и восстановление в отдельную тестовую БД на вымышленных данных. Восстановление рабочей базы — отдельная разрушительная операция, требующая явного разрешения.

При штатной ежедневной работе допустима потеря изменений до суток; при неудачных запусках — после последней успешной копии. Старые копии не переписываются вслед за удалением записей. Полное восстановление возвращает состояние всех домов на дату копии, включая позднее удалённые записи. Это не корзина и не пользовательская история.

## Даты, дела и напоминания

Продуктовые правила B06 закреплены в [делах](PRODUCT.md#дела) и [календаре и напоминаниях](PRODUCT.md#календарь-и-напоминания). Код, схема данных и механизм доставки ещё не реализованы.

Запланированная дата дела, необязательное время, дата фактического выполнения и техническое время отметки имеют разные значения. Отсутствующее время не подменять введённой пользователем полуночью. Принадлежность дела — «Семья» либо карточка своего дома; она отделена от автора и фактического исполнителя. Сервер проверяет принадлежность связанных карточек дому и прежние права доступа.

Сервер хранит и проверяет приоритет дела. При синхронизации приоритет передаётся вместе с записью дела и сохраняется в Room для одинаковой сортировки с сетью и без неё.

Следующая дата повторяющегося дела рассчитывается от фактической даты выполнения, в том числе исправленной пользователем. Сервер проверяет наличие запланированной даты у повторяющегося дела и допустимость интервала из согласованного набора в PRODUCT.md. Если в целевом месяце нет нужного числа, использовать его последний день. Отсчёт следующего интервала снова ведётся от фактического выполнения. Повторная отправка отметки и синхронизация не должны создавать дубли следующего повторения; одинаковые отметки, исправление даты и снятие отметки подчиняются B07.2: ручные правки полей следующего дела и его выполнение блокируют автоматический пересчёт и отмену предыдущего.

Для семейных дат и определения «сегодня» используется единый часовой пояс дома. При создании дома управляющий выбирает пояс, по умолчанию используется `Asia/Irkutsk`. Хранить выбранный идентификатор зоны у дома. Дата без времени сохраняет календарный смысл; смена пояса телефона не сдвигает событие. Планирование учитывает границы календарных дней в часовом поясе дома.

Главный экран получает актуальные невыполненные дела и неоплаченные покупки/платежи начиная за 3 дня до даты, включая записи с прошедшей датой до выполнения/оплаты. Одно тихое уведомление предназначено каждому участнику за 2 дня в 10:00 по времени дома; время события не меняет этот час. Заметка с датой сама по себе уведомления не создаёт. Сохранение данных и повторный запуск планирования не должны повторять уже доставленное уведомление о том же событии.

Для записи, созданной или перенесённой после расчётного времени уведомления, применять показ на главной по общему правилу без отправки уведомления задним числом. После перезапуска телефона проверить актуальность пропущенного уведомления и показать его однократно, если запись ещё не выполнена/не оплачена; не воспроизводить повторную очередь устаревших напоминаний. Выполнение, оплата и удаление отменяют напоминание, перенос пересчитывает его. Получение изменения с другого устройства обновляет локальный показ и планирование; без обновления данных знание удалённых изменений не предполагается. Без связи напоминания используют последние полученные данные. Изменения требуют доступного сервера по B07.1; действуют правила одновременных изменений B07.2.

Точность доставки до минуты не требуется. Механизм уведомлений и восстановления после перезапуска выбрать перед реализацией с учётом разрешений и ограничений целевых устройств. WorkManager остаётся средством фоновой синхронизации, а не обещанием точной доставки; проверка на Huawei P60 обязательна. Требование уведомлять всех участников не расширяет доступ неактивных участников: после получения отключения клиент скрывает данные и отменяет напоминания по B07.4.

### Покупки, связанные с делом

По B06.6 связь необязательна: у дела несколько покупок, у покупки максимум одно дело. Используются обычные записи покупок и их финансовые результаты; создание и редактирование из дела не создают отдельной копии покупки или второго расхода. Сервер проверяет доступ и принадлежность обоих объектов одному дому. Ограничение одной связи покупки сохраняется и при одновременной привязке с двух устройств; конкретную схему и ограничения хранения определить перед реализацией. Правила обработки конфликта и отказа определены в B07.2–B07.3.

Создание покупки из дела и сохранение её связи должны давать согласованный результат, в том числе при повторе запроса и потере ответа. Отвязка меняет только связь и доступна любому участнику. Допустимое удаление дела убирает его связи без удаления покупок; допустимое удаление покупки сохраняет дело. Сервер сохраняет прежние ограничения удаления, включая возвраты; каскадного удаления содержимого связанного объекта нет.

Статусы, даты, напоминания и финансовые результаты объектов независимы. Покупки относятся к выбранному повторению дела, автоматически не копируются и не переносятся к следующему. Техническое представление повторений должно сохранять эту принадлежность; его выбрать до реализации. Room хранит загруженные связи для чтения без сети; все изменения требуют доступного API по B07.1.

## Huawei, локализация и напоминания

- Основные функции проектируются без обязательной зависимости от Google Play services.
- Целевые устройства первого APK — два Huawei P60. Для одного подтверждены EMUI 14.2.0, сборка 14.2.0.208 и Android API 31. Версию второго телефона и фактическую установку APK проверяет пользователь при QA-прогоне.
- Работа фоновых задач и уведомлений требует проверки на реальном телефоне.
- Продуктовые правила доставки выбраны в B06: одно тихое уведомление за 2 дня в 10:00 по времени дома, без требования точности до минуты. Конкретный механизм и необходимость push-провайдера определить перед реализацией; подключение внешнего сервиса не разрешено одним фактом фиксации требований.
- Пользовательские тексты интерфейса выносятся в ресурсы русского и английского языков. Язык следует системной настройке телефона; форматы даты, времени и суммы определены в [PRODUCT.md](PRODUCT.md#статус-и-область).

## Возможное развитие

Подготовка пользовательских экранов ведётся по [DESIGN.md](DESIGN.md) после уточнения влияющих на них требований. Дизайн разрабатывается в отдельном чате; схема данных и контракт API не выводятся из неподтверждённых макетов.

Текущий объём — личное использование. Разделение интерфейса, логики, хранения и интеграций должно позволять расширять приложение без переработки основной логики.

Реклама, оплата, тарифы, публичная регистрация, веб-клиент и другие платформы не реализуются заранее. Не создавать пустые платёжные компоненты и универсальную систему плагинов. Самостоятельное создание домов пользователями не входит и в обсуждённый будущий сценарий доступа за оплату.
