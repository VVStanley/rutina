# Работа по плану «Рутины»

## Определить текущий шаг

1. Прочитать [AGENTS.md](../../../AGENTS.md) и [основной план](../../../plans/MASTER_PLAN.md). Проверить состояние рабочего дерева, включая новые файлы, и содержимое `plans/`.
2. Использовать шаг, указанный пользователем. Если номер не указан, взять ссылку «Текущий шаг» из основного плана и сверить её со статусами. При завершении всех шагов сообщить об этом.
3. Открыть подплан по ссылке в разделе шага. Если ссылки нет, поискать в `plans/` файл с префиксом `<номер>-` и сверить его содержание с шагом. Переиспользовать единственный подходящий файл. При нескольких кандидатах или несовместимых статусах сверить результаты проверок и текущее состояние проекта. Если противоречие остаётся, показать его пользователю и уточнить, какой план актуален.
4. Если пользователь спросил только о статусе, сообщить номер, статус, путь к подплану и ближайшее действие. При таком запросе оставить файлы без изменений.

## Подготовить или продолжить подплан

- Если подплана ещё нет, изучить требования, архитектуру, макеты и реализацию выбранного шага. Подготовить один файл `plans/<номер>-<тема>.md` с границами задачи, порядком работ, критериями и проверками с ожидаемыми исходами. Сохранить его при поручении подготовить подплан или выполнить шаг. Добавить ссылку и актуальный статус в основной план.
- Если подплан есть, сверить его список работ и записанные результаты с кодом, тестами и доступным Git-состоянием. При поручении подготовить подплан дополнить существующий файл и завершить работу на подготовке. Продолжить с ближайшего незавершённого пункта при поручении выполнять шаг. Для статуса «ожидает проверки» вернуться к указанной проверке. Открытые вопросы, влияющие на поведение, согласовать до реализации зависимой части.
- При смене состояния обновить статус шага в основном плане. В подплане записать сделанное, фактические результаты проверок, блокер при наличии и ближайшее действие. Перенести указатель текущего шага после выполнения необходимых проверок. Соблюдать разрешения на реализацию, установки и Git из AGENTS.md.

## Проверить готовность подплана

- При подготовке подплана выполнить самопроверку. При отдельном запросе «проверь план» оставить файлы без изменений. Если поручено доработать план, исправить подтверждённые пробелы в подплане и повторно проверить затронутые части.
- Сверить требования основного шага, [продукта](../../../docs/PRODUCT.md), [архитектуры](../../../docs/ARCHITECTURE.md) и применимого дизайна с доступным состоянием проекта. Проверить, что шаги дают все обязательные результаты и у каждого результата есть наблюдаемая проверка с ожидаемым исходом. Пройти порядок работ как исполнитель и проверить предпосылки, зависимости и разрешения. При затронутых контрактах учесть сохранность данных и совместимость APK. Оценить, можно ли упростить работу с сохранением результата и гарантий.
- Дать короткий вердикт о готовности. Для каждого существенного пробела указать место, последствие и минимальное уточнение. Вопрос продуктового поведения вынести на решение пользователя. Если блокируется часть плана, назвать исполнимые шаги. Судить по результату и проверяемости, независимо от числа разделов. Готовность плана сама по себе не разрешает запуск реализации.

## Спланировать исправления по ревью

- Сверить замечания с текущим кодом по разделу [перепроверки замечаний](../rutina-review/SKILL.md#перепроверка-замечаний). В план включать подтверждённые и ещё актуальные проблемы. Сохранять исходные номера замечаний, если они есть. Если несколько замечаний имеют одну подтверждённую причину, запланировать одно исправление с проверкой всех затронутых сценариев.
- Для каждой группы указать минимальное изменение, порядок и зависимости, ожидаемый результат и конкретную проверку. Для нескольких локальных исправлений достаточно короткого списка. Для связанной работы с API, миграциями или несколькими шагами использовать соответствующий подплан. Обновлять его только по поручению пользователя.

## Выполнить согласованный шаг

При поручении реализации выбрать ближайший незавершённый пункт и выполнить минимальное изменение по [правилам кода](../../../docs/CODING_STANDARDS.md). Для рефакторинга определить сохраняемое поведение, использовать подходящую проверку до изменения и повторить её после. Добавить узкий тест, если иначе существенный риск регрессии остаётся без покрытия. При изменениях кода применить [rutina-code-validation](../rutina-code-validation/SKILL.md).
