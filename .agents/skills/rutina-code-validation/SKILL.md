# Проверка кода «Рутины»

Использовать [CODING_STANDARDS.md](../../../docs/CODING_STANDARDS.md) как источник требований к коду, [структуру проекта](../../../docs/ARCHITECTURE.md#структура-проекта) как схему размещения и зависимостей, [AGENTS.md](../../../AGENTS.md) как источник рабочих ограничений и [README.md](../../../README.md) как источник команд проекта.

## Порядок проверки

1. Определить режим и область работы. При реализации проверять изменённый код, включая новые файлы, и непосредственно затронутые контракты. При отдельной проверке правил сохранять исходники. Для проверки корректности реализации и её соответствия требованиям применять [rutina-review](../rutina-review/SKILL.md). Если Git недоступен, сравнить файлы с доступной исходной версией и указать ограничение, если исходной версии нет.
2. Сразу после реализации запустить форматтер и линтер для каждой затронутой части. Исправить все замечания в области задачи и повторить проверки после правок. При отдельной проверке правил использовать команды без автоисправлений. Сохранить пользовательские изменения и не ослаблять правила проверок ради успешного прогона.
3. Запустить проверку типов Python, компиляцию Kotlin и тесты по применимости к изменениям. Для Android использовать проверку форматирования Kotlin и Android Lint. Для тестов с БД убедиться, что команды используют отдельную тестовую PostgreSQL. Использовать настроенные команды проекта. Если команда, зависимость или среда недоступна, продолжить ручную проверку и назвать конкретный блокер. Не подменять штатную проверку произвольной командой и не устанавливать зависимости без разрешения.
4. Просмотреть итоговые изменения по пунктам ниже. При реализации исправить нарушения в области задачи и повторить затронутые проверки.

## Ручная проверка

- **Структура проекта.** Сверить расположение и назначение новых, изменённых и перемещённых файлов с архитектурой. На сервере сравнить пакет функции с [примером `purchases/`](../../../docs/ARCHITECTURE.md#пример-пакета-purchases). Проверить размещение SQL в `db/queries/`, прямые импорты из файла нужной области и пустой `queries/__init__.py`. На Android проверить размещение в `app/`, `core/` и `feature/<функция>/` с отдельными `ui/` и `data/` по применимости. Проверить обоснование новых корневых каталогов и Gradle-модулей. Отсутствие файла без текущей ответственности допустимо.
- **Типы и статусы.** Проследить типы от HTTP до прикладной операции и хранилища, а на Android от API и Room до состояния экрана. Проверить аннотации Python и типизированные результаты, отсутствие возвратов `dict` в Python и подмены типов через `Any`. В Kotlin структура с известными полями имеет объявленную модель. Для нового или изменённого статуса найти его enum и проверить текущую схему, запросы, переходы и общий контракт. Учитывать отдельные правила для выпущенных миграций и тестов контракта.
- **Слои и DI.** Проследить путь от роутера через одну прикладную операцию к запросам, убедиться, что права, правила и транзакция принадлежат сервису. Сверить затронутые импорты с [правилами размещения](../../../docs/ARCHITECTURE.md#правила-размещения), включая обратные зависимости из запросов, моделей и типов и циклы между сервисами. Проверить, где собираются и передаются зависимости, как Compose и `ViewModel` получают данные и кто владеет каждым затронутым бизнес-правилом.
- **Настройки, ошибки и логи.** Проверить единый источник настроек, именование значимых констант, базовый `AppError` для собственных исключений Python, стабильные коды API и локализованные сообщения Android. Проверить однократную регистрацию неожиданного сбоя на границе, связь с `request_id` для HTTP и отсутствие чувствительных данных в логах.
- **Тесты и совместимость.** Проверить независимость тестов, применение нужной группы и покрытие затронутых рисков. Для изменений записи учесть права, изоляцию домов, повторы и конкурентность по применимости. При изменениях схемы или API проверить миграции и сценарии установленного APK, которые затрагивает изменение.

## Итог проверки

Сначала перечислить оставшиеся нарушения с файлом, строкой и конкретным исправлением. Затем кратко указать исправленное и результаты реально выполненных команд. Для каждой пропущенной проверки назвать причину. Например, до появления настроек первого каркаса доступна ручная проверка, а запуск линтера или сборки остаётся неподтверждённым.
